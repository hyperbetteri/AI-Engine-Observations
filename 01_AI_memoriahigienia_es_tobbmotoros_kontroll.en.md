# AI Memory Hygiene and Multi-Engine Control

**A public case study on stabilising a long-term human–AI workflow**

Author: Almási Andor · Public version: June 2026 (v1.0)

> **Publication note.** This document presents the lessons of a specific, long-term human–AI workflow in a generalisable form. It contains no executable internal prompts, no full memory import, no private project data, no exact code identifiers, no entity lists and no sensitive operational logs. The aim is to present the problem, the decisions of principle and the outcome in an accessible way.

## 1. Abstract

This study describes the stabilisation of a long-running human–AI collaboration in a public form, with details protected. The starting problem was that persistent AI memory, project context, old development states and current tasks had begun to blend together. This is not merely a cosmetic flaw: in long-term use it can also pose risks to accuracy, work organisation and safety.

The essence of the intervention was not to make the AI system keep as much information in mind as possible, but to ensure that only information at the right level of abstraction stayed in active memory. Detailed formulas, project architectures, and legal, technical or methodological rules were kept in a separate, verifiable source layer.

The result was a layered operating model: a short operating core, a separate deep-work starter, a detailed source in the form of a masterfile, a project archive, a quarantine for corrupted or outdated items, and an external control engine. The model aims to improve accuracy, task discipline and long-term usability.

> **Main claim:** In long-term AI use, memory is not a complete knowledge base but an operating compass. Detailed knowledge that needs verification must be kept in a separate source layer.

## 2. The problem

The persistent memory features of large language models are useful because they can retain user preferences, operating principles and recurring project contexts. The same capability, however, also carries risk when memory tries to hold too many details, outdated states or data that demands precision.

In the case examined, several layers of memory and of the working environment became mixed: basic style, task-handling rules, an old project chronicle, technical formulas, version labels, the division of roles between different AI engines, and leftovers from earlier development. This created a situation in which the system sometimes assumed too much, brought back old structures, or handled details at the wrong level.

- Memory could start to behave as a source where it should only have been a compass.
- Old project material could leak back into conversations where it was not relevant.
- Formulas, versions and identifiers proved especially prone to distortion.
- The roles of the main AI engine and the checking engine could have blurred had the roles not been separated.

So the problem was not that the AI "did not remember enough", but precisely that its memory was not layered cleanly enough. The goal was to reduce the amount of active memory and improve its quality.

## 3. Goal of the intervention

The goal of the intervention was to build a stable AI memory-hygiene model that is also intelligible from a public point of view. The focus was on three questions: what should stay in active memory, what should only be a separately launchable deep-work context, and what should remain in a verifiable external source.

1. The core operating rules should be short, stable and resistant to distortion.
2. Detailed project logic, formulas, metrics and identifiers should not be reconstructed from internal memory.
3. Deeper analytical work should have its own starter material that activates the appropriate frame of attention without overwriting the core memory.
4. Old, corrupted or uncertain content should not automatically find its way back into persistent memory.
5. The control engine should help detect errors, but should not become a copy of the main engine or the one giving it orders.

## 4. Key concepts

The following concepts are needed for the public interpretation of the study. The names are generalised; they do not describe the internal technical workings of any specific platform.

- **Operating core:** a short, permanent compass covering language, style, task discipline, source handling and basic safety principles.
- **Deep-work starter:** a separate thread-starter or context-starter that activates a frame of attention for specialised, complex work, but is not a permanent memory import.
- **Masterfile:** a detailed, verifiable source document. This is where formulas, metrics, versions, exact rules and longer project architectures belong.
- **Project archive:** a repository for historical or development material. It can be useful, but it is not necessarily a current operating rule.
- **Quarantine:** a separated layer for corrupted, outdated, duplicated or conflicting information. Nothing returns from here automatically.
- **Control engine:** another AI system or checking perspective that can help identify errors but does not take over the role of the main working engine.

## 5. The layered solution model

The central decision of the intervention was layering. Instead of putting every seemingly important piece of information back into persistent memory, each item was placed according to its own level of risk and required precision.

| Layer | Role | Public rationale |
|---|---|---|
| Operating core | Short, persistent operating compass | Reduces noise and the unnecessary resurfacing of context. |
| Deep-work starter | Manual launch of specialised work | Keeps complex project logic out of normal conversations. |
| Masterfile | Detailed, verifiable source of truth | Exact formulas, versions and rules do not come from synthesis. |
| Project archive | Historical development material | Preserves the past without automatically making it current. |
| Quarantine | Isolation of corrupted or uncertain content | Prevents recontamination. |
| Control engine | External checking perspective | Improves error detection without mixing up the roles. |

*Table 1: The public layered AI memory-hygiene model*

The main advantage of the layered model is that memory does not try to retain everything. Only the short compass stays active for normal operation. Detailed knowledge is brought in only when the task genuinely calls for it, and even then from a verifiable source.

## 6. Why can the full method not be published?

With an intervention like this, it is natural to ask why it is not advisable to make every concrete step, prompt and internal detail public. The answer is not secrecy but risk management.

- The exact prompts and memory items may contain personal or project-sensitive operating patterns.
- Formulas, version references and identifiers can be misunderstood or wrongly reused without context.
- Publishing old errors in detail could produce a "copyable error catalogue" that others misapply in other systems.
- The operational division of roles between specific engines is not a general recipe but a decision tailored to a particular working environment.

What can be shown publicly, therefore, is the model in principle, the problem statement, the layering, the rationale and the outcome. A detailed operational log is of no public benefit, yet it could lend itself to misuse, misunderstanding or faulty reproduction.

## 7. Results and verification criteria

After the intervention, the system's operation became simpler and cleaner. The main value was not the appearance of a new feature but the removal of unnecessary elements that were prone to distortion.

| Area | Before the intervention | After stabilisation |
|---|---|---|
| Role of memory | Tried to carry too many details | Short operating compass |
| Formulas and versions | Could also appear in a memory layer prone to distortion | Only from the masterfile or a clean source |
| Project chronicle | Could leak back into normal tasks | Goes to the project archive or a separate source |
| Deep work | Could get mixed up with normal operation | Can be activated with a separate starter |
| Control engine | Could potentially over-steer the main engine | Stays in a separate role as a checking perspective |

*Table 2: Comparison of the state before and after stabilisation*

### 7.1. Verification test

The core of verifying the stabilised state was a cold-start test: the system had to briefly summarise its active operating profile without bringing back any project chronicle, entity list, code, formula or internal identifier. The aim of the test was not completeness of content but an examination of layer discipline.

Based on the test, the core operating compass proved functional: the system returned the main rules and did not try to reconstruct the detailed technical content from memory. This is an essential result for long-term usability.

## 8. Generalisable lessons

1. The quality of persistent memory matters more than its quantity.
2. Internal memory is not suitable for carrying every piece of precision-critical data.
3. Formulas, versions, and legal and technical data require a verifiable source layer.
4. A long project chronicle and the active operating profile are not the same thing.
5. Multi-engine checking is useful, but only with role discipline.
6. A good system does not always retain more information; rather, it knows better what must not be handled from memory.

## 9. Risks and limitations

The model does not solve every problem related to AI memory. Persistent memory can still be synthetic, abstracting and system-dependent in nature. Therefore, source-based verification remains necessary in every area with accuracy-related, legal, technical, medical or financial consequences.

- Memory hygiene does not replace professional validation.
- A masterfile is only reliable if it is versioned, maintained and verified.
- The control engine is not an objective judge but another modelling perspective.
- Old archives can be useful but can easily bring back outdated or conflicting states.
- Correcting memory too frequently can itself cause instability.

## 10. Practical recommendations

| Recommendation | Rationale |
|---|---|
| Keep the core memory short. | A short operating core distorts less and brings back less off-task content. |
| Separate the deep-work context. | Complex projects should not burden everyday tasks. |
| Use a masterfile for detailed rules. | Exact formulas, metrics, versions and legal/technical data do not belong in memory. |
| Keep a quarantine for corrupted items. | Instead of deleting or rebuilding, isolate and assess first. |
| Test operation with a cold start. | This reveals whether the system brings back unwanted project leftovers. |
| Treat the control engine as a control. | It should not be a second main engine, and it should not automatically overwrite the logic of the first system. |

*Table 3: Public practical recommendations for AI memory-hygiene work*

## 11. Conclusion

The main lesson of the case presented is that the quality of long-term AI use does not depend solely on the capabilities of the model or the skill of the prompts. Memory hygiene is at least as important: consciously deciding what goes into active memory, what stays in a separate source, and what must be kept in quarantine.

A stable system is not one that remembers everything, but one that keeps the right information in the right layer. Active memory is an operating compass, not a complete knowledge base. Detailed knowledge should be handled from sources, not from synthetic recollection.

This principle is applicable not only to one specific human–AI workflow but also as a more general rule of AI-use hygiene: in long-term collaboration, accuracy, layer discipline and source handling matter more than the quantity of memory.

## 12. Appendix: public checklist

The list below contains non-sensitive checkpoints that can also be applied in other AI memory-hygiene work.

- [ ] Is there a short, stable operating core?
- [ ] Is the core memory separated from the deep-work context?
- [ ] Is there a separate masterfile or verifiable source layer for exact data?
- [ ] Have formulas, versions and identifiers been removed from active memory where they are prone to distortion?
- [ ] Is there a quarantine for old, corrupted, duplicated or conflicting items?
- [ ] Is the role of the control engine checking rather than commanding?
- [ ] Has a cold-start test been carried out without the project chronicle or internal codes being brought back?
- [ ] Is it clear when a clean source or the masterfile must be requested?
- [ ] Does the system refrain from automatically generating new material without an explicit request?
- [ ] Is the publishable summary free of sensitive internal prompts, identifiers and private project data?
